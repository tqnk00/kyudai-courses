# src — 授業さがし を作るコード

公式サイトから情報を取って SQLite に貯め、そこから静的なページを書き出す。
使い方（更新のしかた）は一つ上の [README.md](../README.md) を参照。ここはコードを読む人向け。

## 読む順番

1. `run.py` の `update()` … ふだんの更新で何がどの順に動くかが分かる
2. `site_data.py` … サイトに載せるデータの形を決めている。先頭のコメントに項目名の対応表（`c` `t` `tg` …）
3. `build_site.py` … 上のデータを `site_template.html` に流し込むだけ
4. `site_template.html` … 画面。末尾の初期化（`applyHash(); render();`）から `render()` を追うと全体が見える
5. 取得まわりは必要になってから

## ファイルの役割

| まとまり | ファイル | 役割 |
|---|---|---|
| 入口と設定 | `run.py` | ジョブの入口。`update` `daily` `rooms` `site` `deploy` など |
| | `config.py` | 年度、置き場、開講期や科目区分のまとめ方 |
| | `db.py` `power.py` | SQLite の定義と接続、処理中のスリープ抑止 |
| Campusmate から取る | `campusmate.py` `sweep.py` | 開講期ごとの一覧を取る |
| | `detail.py` | 科目ごとのシラバス本文を取る |
| | `extract.py` `grading.py` | 本文から項目（学部・学年・コマ・成績評価）を抜き出す |
| Campusmate 以外から取る | `lit.py` | 文学部のシラバス（別サイト）。DBには入れず `data/lit-courses-年度.json` に保存 |
| | `timetable_pdfs.py` | 各学部の時間割PDFの在りか（URL・掲載ページ・学期）と取得 |
| | `timetable_rooms.py` `timetable_econ.py` | PDFから「科目 → 教室」と、シラバスが無い科目を拾う |
| | `core_btable.py` | 基幹教育のB表から教室と事前申請の印を拾う |
| | `class_days.py` | 公式の授業日程（`config.CALENDAR`）から、開講期×曜日ごとの授業日を出す。カレンダー書き出し用 |
| サイトを作る | `site_data.py` | DB と `data/*.json` を合わせ、ページ用のJSONと詳細の分割ファイルを作る |
| | `build_site.py` `site_template.html` | ページの組み立てと、画面そのもの |
| その他の出力 | `report.py` | 実測レポートと CSV / JSON の出力（サイトには使わない） |
| テスト | `tests/test_*.py` | 一時DBと模擬応答で動く。実サイトには触れない |
| | `tests/browser_all.cjs` | 実ブラウザで画面を操作する確認（先頭のコメントに準備と実行の方法） |

## データの流れ

```
Campusmate ─ sweep ─ detail ─ extract ─→ SQLite ─┐
文学部サイト ─ lit ───────────→ data/lit-courses-年度.json ─┤
時間割PDF ─ timetable_* / core_btable ─→ data/*.json ───────┼─ site_data ─ build_site ─→ index.html
                                                              │                          └ details-年度/NN.json
```

文学部と時間割PDFの情報は SQLite を通らず、`data/` の JSON からサイト生成のときに合流する。
`data/` の JSON は履歴に入れてあり、`run.py rooms` と `lit.py` で作り直せる。

## 置き場

| もの | 既定の場所 | 環境変数 |
|---|---|---|
| DB | `~/syllabus-db/kyudai.db` | `SYLLABUS_DB_PATH` |
| ビルド出力 | `~/syllabus-db/exports/` | `SYLLABUS_EXPORT_DIR` |

| 取り込みデータ | `src/data/`（リポジトリの中） | `SYLLABUS_DATA_DIR` |

DB・出力・PDFは合わせて数十MBあり、OneDrive 配下に置くと作り直すたびに同期が走るので外に出してある。

## コマンド

Windows では `python` ではなく `py` を使う（`python` はストア版の空の実行ファイルに当たることがある）。

```
py run.py update            ふだんの更新。取り直し → 生成 → 配置 → テスト → 公開するか確認
py run.py daily             一覧を取り直し、新しい科目の本文だけ取る → 抽出 → サイト生成
py run.py weekly            全科目の本文を取り直して差分を見る（重い）
py run.py rooms --refresh   時間割PDFを取り直し、教室と事前申請を作り直す
py lit.py                   文学部を取り直す
py run.py site              サイト生成だけ（通信なし）
py run.py deploy            生成物を公開リポジトリの直下に置く（push はしない）
py run.py extract           保存済みの本文から抽出し直す（通信なし）
py run.py report            実測レポートと CSV / JSON
py run.py changes --days 14 直近の本文の変化の件数
```

- `--set`: `all`（全開講期。既定）、`phase1`（後期＋通年）、`autumn`、`spring`、`full`（通年のみ）。
  一部の開講期だけ回しても、対象外の開講期の科目はサイトから消えない（開講期ごとに最後の巡回と比べる）
- `--workers`: 1〜5、既定4。本文取得の同時接続数
- `site`・`report` は学部のみが既定。`--all` で大学院・判定不能も含める

## テスト

```
py -m unittest discover -s tests
```

一時DBと模擬応答を使い、実際のDB・大学サイトにはアクセスしない。
画面の確認は `tests/browser_all.cjs`（Chrome / Edge / Safari相当、iPhone / iPad / Android の8種類の画面）。

## 年度を変えるとき

授業日程（カレンダー書き出し用）は `config.CALENDAR` に年度ごとに写す。全学の日程を土台に、
学部ごとの違いを差分で書く。写したら `tests/test_class_days.py` が「月〜金がどれも15回・
クォーターは8回」になるかを確かめる（祝日や振替の写し忘れがあると回数が合わない）。
各学部の授業日程表の在りかは `config.py` の `source` にある。

`config.YEAR` と `--year` で大半は切り替わるが、時間割PDFは年度がファイル名とURLに入っている。
`timetable_pdfs.py` の `PDFS` と `SEASON`、それを名前で引いている `timetable_rooms.py` `timetable_econ.py`
`core_btable.py` のファイル名を新年度のものに直すこと。

過去のレビューと設計の記録は [../docs/history/](../docs/history/) にある。

## 仕様書からの変更点（実測で判明したこと）

仕様書は「2026-09-05 時点で実際にリクエストを送って確認したもの」だが、
実装中に次の6点が仕様書と違っていた。

### 1. 一覧検索はブラウザ自動化なしで動く

仕様書2.2は「`form.submit()` では動作しない」「ブラウザ自動化で操作するのが確実」としているが、
素の HTTP POST で動く。鍵は2つ:

- 検索ボタンの `exec()` は **`buttonName` を `searchKougi` に書き換えて submit するだけ**
  （`js/main.js` で確認）。`buttonName` が空のまま POST すると8.5KBのエラー殻が返る。
  仕様書が観測した「殻が返る」現象はこれ。
- 表示件数200件への切り替えは `doPaging()` が `value(maxCount)` を書き換える。
  このとき **`value(pageCount)` は空** にすること。ページ番号を入れると `maxCount` が無視される。

セッションCookieは必要（エントリURLをGETして取得）。
結果、後期系＋通年系10値・4,111件の一覧スイープが **129秒** で終わる。

### 2. 詳細ページには様式が3つある

仕様書2.1は `科目名称` 〜 `合理的配慮について` の1様式だけを想定しているが、実際は3つある。
実測の内訳は **A: 2,941件 / B: 1,155件 / C: 15件**。

| | 様式A（全学標準） | 様式B（旧様式） | 様式C（医学部の統合科目） |
|---|---|---|---|
| 開始 | `科目名称` | `講義科目名` | `授業科目名` |
| 終了 | `合理的配慮について` の手前 | `PAGE TOP` の手前 | `PAGE TOP` の手前 |
| HTMLサイズ | 約520KB | 約200KB | 約200KB |
| 学部フィールド | `学部カテゴリ` | `開講学部・学府` | `対象学部等` |
| 成績評価 | `授業科目の成績評価の方法について`（半構造化） | `試験／成績評価の方法等`（自由記述） | なし |
| `更新日付` の位置 | 冒頭付近 | 末尾 | 冒頭付近 |

`科目名称` だけを探すと様式B・Cを取りこぼす。さらに **様式Cは本文中の表見出しに
`科目名称` が現れる**（構成科目の一覧）ため、単純に最初に見つかった開始マーカーを使うと
本文の途中から切り出してしまう。`detail.py` は **開始位置が最も早い様式を選ぶ**。

### 3. 講義コードは `\b2\d{7}[a-zA-Z]?\b` では足りない

仕様書2.5の正規表現では取りこぼす形式が実在する。

- **`S` 始まり**: `S26831604`（総合演習など）。先頭に英字が付くため `2\d{7}` に一致しない
- **`24` 始まり**: `24638690`（低年次総合カリキュラム）。2026年度の一覧に載るが年度接頭辞が26でない

本実装は **HTMLを正規表現で舐めるのをやめ、結果テーブルの講義コード列（2番目の`<td>`）を直接読む**。
コードの書式に依存しないので、この種の例外に影響されない。
正規表現は `config.py` に残してあるが、パースには使っていない。

### 4. `対象学部等` は学部名として使えない

仕様書2.1は「`対象学部等` は学部までで学科を持たない」としているが、実際には
**学年が入っていることの方が多い**（`学部2年 学部3年 学部4年`、`2023年以前入学者` など）。
学部名として信頼できるのは様式Aの `学部カテゴリ`（`法学部` `経済学部` `基幹教育科目`）、
様式Bの `開講学部・学府`（`法学府` `歯学府`）のほう。

`course_structured` には両方入れてある。

- `faculty` … 学部カテゴリ / 開講学部・学府（学部の判定はこちらを使う）
- `faculty_raw` … `対象学部等` の生値

### 5. 学部／大学院の判定材料が無い科目が283件ある

学部・学府・対象学年・ナンバリングコードが**すべて空**の科目がある
（`26771xxx` / `26775xxx` の「課題探究チュートリアル」系。卓越大学院プログラムと思われる）。
学部と決めつけず `is_undergrad` を **3値（1=学部 / 0=大学院 / NULL=判定不能）** にしてある。

判定に使っている材料は次の順:

1. `学部カテゴリ` / `開講学部・学府` / `授業科目区分` に `学府` `大学院` `専門職` が含まれるか
2. `対象学年` に `修士` `博士` が含まれるか
3. **科目ナンバリングのレベル桁**（`KED-LCB2124W` の `2`）。5以上が大学院。
   学部・学府がはっきりしている2,531件で照合したところ例外なく一致した

判定不能283件の扱いは要判断。学部として履修対象に含めるなら明示的に埋めること。

### 6. 学科指定 `（経経）（経工）` は後期系にほとんど無い

仕様書2.1の「学科指定は講義名に埋め込まれている」は正しいが、後期系4,111件で
この書式は **2件だけ**（`基礎計量経済学Ⅰ/Ⅱ（経工）`）。経済学部の講義名の末尾括弧は
大半が副題（`（国際関係論）`）か英語表記（`（英語経済）`）で、担当教員名（`（山下先生）`）
まで混ざる。仕様書の例（`マクロ経済学Ⅰ（経経）`）は春学期の科目。

一律に括弧を学科指定として拾うと誤りが大量に出るため、

- `department` … `config.DEPARTMENT_CODES` の既知の略号に一致したものだけ（実測2件）
- `title_suffix` … 末尾括弧の生値（実測293件）。Phase 2 の名寄せ用に残す

の2列に分けてある。新しい学科略号が見つかったら `DEPARTMENT_CODES` に追記すること。

## 実装上のメモ

- **接続の使い回し**: 詳細ページ取得でリクエストごとに `httpx.Client` を作ると
  TLSハンドシェイクのぶん約2倍遅い（実測 2.1s/件 → 1.1s/件）。スレッドごとに1本使い回す
- **同時接続は4本**。仕様書5章の「3〜5本まで」に従う
- **生HTMLは保存しない**。本文だけ残して即破棄（仕様書5章）
- `university_id` を全テーブルの主キーに含めてある（仕様書8章）
- スキーマ変更は `db.py` の `MIGRATIONS` に追記すれば既存DBに反映される
- **本文ハッシュの安定性を確認済み**: 同じ20件を取り直したところ `body_sha256` は全件一致した。
  仕様書2.6の「抽出後の本文はバイト単位で一致する」は成り立っている
